# Шпаргалка к защите ЛР1–ЛР2 (Верификация ПО)

## Как запустить

```bash
.venv/bin/python -m pip install -r requirements.txt
```

```bash
.venv/bin/python manage.py migrate
```

```bash
.venv/bin/python manage.py seed_data
```

```bash
.venv/bin/python manage.py runserver
```

Сайт: http://127.0.0.1:8000/ — вход `client1 / client12345` (клиент), `manager / manager12345` (сотрудник).

Тесты и покрытие:

```bash
.venv/bin/python -m pytest --cov --cov-report=term-missing
```

Ожидаемо: `194 passed, 6 xfailed`, покрытие **94%**.

## Ответы на вопросы

**1. Этапы жизненного цикла тестирования? С какого этапа начинается работа тестировщика?**
Анализ требований → планирование → разработка тест-кейсов → подготовка окружения → выполнение тестов →
регистрация дефектов и повторная проверка → отчет и завершение. Тестировщик подключается с **анализа требований** —
дефект в требованиях дешевле всего исправить (как в ЛР1: нашли непроверяемые требования до тестов).

**2. Что такое требование? Зачем, кто источник, кто потребитель?**
Требование — описание того, что система должна делать или каким свойством обладать. Нужно, чтобы все одинаково понимали,
что строим, и чтобы было с чем сравнивать результат. Источники: заказчик, пользователи, законы и стандарты, бизнес-процессы.
Потребители: разработчики, тестировщики, аналитики, менеджер проекта, заказчик (приемка).

**3. Уровни требований?**
- Бизнес-требования — зачем нужна система, какие цели бизнеса (БТ-1…БТ-4).
- Пользовательские — что пользователь может делать с системой (use case UC-1…UC-8).
- Функциональные — что конкретно делает система (FR-01…FR-22).
- (Плюс нефункциональные — каким качествам должна отвечать.)

**4. Функциональные vs нефункциональные?**
Функциональные — **что** система делает (добавить в корзину, оплатить заказ).
Нефункциональные — **как хорошо** она это делает: скорость, безопасность, надежность, удобство, переносимость.

**5. Use case и актор?**
Use case (вариант использования) — сценарий взаимодействия пользователя с системой для достижения цели («Оформить заказ»).
Актор — внешняя по отношению к системе роль (человек или другая система), которая взаимодействует с ней: Гость, Клиент, Сотрудник, Внешние API.

**6. Модульное vs интеграционное vs системное?**
- Модульное — один модуль/класс изолированно, зависимости заменены моками (`Cart` с мок-сессией).
- Интеграционное — взаимодействие нескольких компонентов: код + БД, код + внешний сервис.
- Системное — вся система целиком как черный ящик на соответствие требованиям.

**7. Белый, черный, серый ящик?**
- Белый — тесты пишутся со знанием кода (покрываем ветки, условия).
- Черный — только по требованиям, вход → ожидаемый выход, код не смотрим.
- Серый — частично знаем устройство (например, структуру БД или API), но тестируем снаружи.

**8. Позитивное vs негативное? Как система должна вести себя на негативный тест?**
Позитивное — корректные данные, проверяем, что работает. Негативное — неверные данные/действия, проверяем, что система
не ломается. Правильная реакция: понятное сообщение об ошибке или код 4xx, данные не испорчены, нет 500 и падений
(пример: оплата отмененного заказа → сообщение, статус не меняется).

**9. К какому методу относятся мои тесты?**
- Модульные — **белый ящик** (знаем внутренности, мокаем зависимости).
- Интеграционные — **серый ящик** (знаем модели и БД, но проверяем через формы/HTTP).
- Сценарные — ближе к **черному/серому**: ходим по HTTP как пользователь и проверяем результат по требованиям и диаграмме состояний (плюс заглядываем в БД).

**10. Уровни представления, бизнес-логики, данных? К каким относятся мои тесты?**
- Представление — интерфейс/HTML/ответы HTTP (что видит пользователь).
- Бизнес-логика — правила: скидки, лимиты корзины, переходы статусов.
- Данные — хранение и целостность в БД.
Мои: юнит — бизнес-логика; интеграционные — бизнес-логика + данные (+ представление через тестовый клиент);
сценарные — все три слоя, проходят от HTTP-запроса до записи в БД; часть тестов проверяет текст страницы — представление.

**11. Регрессионное тестирование? Почему тест на дефект оставляют?**
Повторный прогон тестов после изменений, чтобы убедиться, что старое не сломалось. Тест, нашедший дефект, оставляют,
чтобы дефект не вернулся незаметно при следующих правках (`test_defects.py`).

**12. Что выявляет интеграционное тестирование, если модули уже проверены?**
Ошибки на стыках: неверные форматы данных между компонентами, ошибки SQL/ORM и ограничений БД, транзакции,
настройки, поведение реального внешнего сервиса (таймауты, 500). Пример: юнит-тесты с моками не нашли бы BUG-4 —
он проявился только с настоящей SQLite.

**13. Сценарный vs интеграционный vs E2E? Пирамида тестирования?**
- Интеграционный — проверяет взаимодействие 2+ компонентов, обычно одно действие.
- Сценарный — последовательность действий по бизнес-сценарию (корзина → заказ → оплата), проверка переходов.
- E2E (сквозной) — вся система как у пользователя: реальный браузер, сервер, БД (например Selenium/Playwright).
Пирамида: внизу много быстрых **юнит**-тестов, в середине меньше **интеграционных**, наверху мало медленных **E2E/UI**.
Чем выше — тем дороже и медленнее тесты, поэтому их меньше.
